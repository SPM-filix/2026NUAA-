## 1. 目的

验证系统在并发抢购、重复提交、重复核销场景下是否满足核心业务不变量：

1. 商品库存不超卖；
2. 用户积分不扣成负数、不重复扣减；
3. 同一幂等键只生成一笔订单；
4. 核销码只能被核销一次；
5. 并发下不出现 5xx。

## 5. 延迟与吞吐

单次并发批次的端到端延迟（含公网 RTT）：

| 场景 | 并发数 | p50 (ms) | p95 (ms) | max (ms) | 批次耗时（≈max） | 吞吐（约） |
| --- | --- | --- | --- | --- | --- | --- |
| S1 库存抢购 | 50 | 288.5 | 353.7 | 360.9 | ≈0.36 s | ≈138 req/s |
| S2 幂等键 | 10 | 480.1 | 481.7 | 481.7 | ≈0.48 s | ≈21 req/s |
| S3 核销 | 10 | 73.9 | 84.6 | 84.6 | ≈0.08 s | ≈118 req/s |
| S4 扣分 | 5 | 100.3 | 105.4 | 105.4 | ≈0.11 s | ≈47 req/s |

说明：

- 吞吐按“请求数 ÷ 批次耗时”估算，属于瞬时突发值，不代表持续压测能力。
- S2 延迟明显偏高是预期行为：10 个请求同时争抢同一用户的积分行与同一幂等键，后到请求需要等待前一笔事务提交/回滚，再回查首笔订单返回；它换来的是“只成交一次”。
- S1 的失败请求在商品库存已被扣完后立即返回 3002，不再进入扣积分阶段。

## 6. 并发控制实现对应关系

| 不变量 | 实现 |
| --- | --- |
| 库存不超卖 | `UPDATE product SET stock = stock - ?, version = version + 1 WHERE id = ? AND stock >= ? AND version = ?`，影响行数为 0 时重读并返回 3002 |
| 库存重试可见性 | 乐观锁冲突后使用 `SELECT ... FOR UPDATE` 重读，避免 REPEATABLE READ 快照导致重试反复失败 |
| 积分不扣负 | `UPDATE user SET points_balance = points_balance - ? WHERE id = ? AND points_balance >= ?`，0 行返回 3001 |
| 幂等 | 唯一索引 `(user_id, idempotency_key)` + 冲突回查首笔订单 |
| 核销一次性 | 条件更新 `status = 'COMPLETED' WHERE id = ? AND status = 'PENDING' AND redeem_expire_at > NOW()` |
| 无 5xx | 业务错误统一返回 200 + 错误码，未预期的唯一键冲突也做了回查兜底 |

## 7. 发现与修复

测试前已修复的并发相关缺陷：

- **DEF-001**：库存被并发扣完后，后续请求错误返回 `3013 数量非法` 而不是 `3002 库存不足`。修复方式是把“数量 1–5”和“库存是否足够”拆成两个判断；本次 S1 的 49 笔 3002 验证修复生效。

本次测试暴露的可改进点（未影响结果）：

1. **管理员积分调整不是原子更新**：`AccountService.adjustPoints` 采用“读余额 → 计算 → 写回”，并发调整同一用户时可能丢失更新。当前后台单人操作、风险低；若后续开放批量调整，应改为 `points_balance = points_balance + ?` 条件更新。
2. **幂等请求的重试延迟**：S2 的 p50 接近 500 ms，主要消耗在等待首个事务完成。前端已有按钮防重，真实用户场景可接受；如需进一步优化，可在应用层对同一 key 做短时合并。

## 8. 局限性

- 单客户端突发并发，不是持续压力测试；未测 10 分钟以上稳定性、内存泄漏与连接池耗尽。
- 未使用 JMeter/wrk 等专业压测工具，吞吐数字仅供量级参考。
- 未覆盖多实例部署；当前单实例 + 单 MySQL，结论不能直接外推到集群。
- 公网 HTTP 延迟占比不小，纯服务端耗时会更低。
- 未测试撤销窗口、取消退分等写路径的并发。

## 10. 结论

在上述环境与场景下：

- 50 并发抢 1 件库存，**无超卖**；
- 同一幂等键 10 并发，**只生成一笔订单、只扣一次积分**；
- 同一核销码 10 并发，**只成功一次**；
- 余额不足的并发兑换，**余额未变负**；
- 全程 **无 5xx**。

并发控制满足阶段③出口要求。剩余风险主要集中在未测的持续压力、多实例部署与后台并发调整积分，已在上文列出。
